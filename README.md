# Mini AI Business Intelligence Assistant

Ask sales questions in plain English; get an answer computed by a real SQL query, with the supporting figures shown.
Stack: **Python · FastAPI · SQLite · OpenAI** (with an offline rule-based fallback). Currency is shown as ₹.

## Setup & run
```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                   # then put your OPENAI_API_KEY in .env
uvicorn app.main:app --reload                          # open http://127.0.0.1:8000
```
The SQLite DB is built from `data/ai_bi_assistant_sales_data.csv` automatically on first start
(`python -c "from app.db import build_database; print(build_database())"` rebuilds it).
Without an API key the app still works using the rule-based interpreter.

## Tests

```bash
pytest -v                                  # 22 tests (API tests skip if FastAPI/httpx missing)

```

## Architecture
```
Browser UI ──POST /ask──▶ FastAPI ──▶ service.ask()
                                         │ 1. interpret question → JSON "plan"
                                         │      OpenAI (temperature 0, JSON mode)  ──fails──▶ rule-based parser
                                         │ 2. validate_plan()   ← safety gate (whitelists + catalog check)
                                         │ 3. analytics.run_plan() → fixed parameterised SQL
                                         ▼
                            SQLite (opened read-only)  ──▶ rows + SQL + params + answer text
```
**Key decision: the LLM never writes SQL.** It only picks one of 5 intents and parameters. Fixed, parameterised queries
do the maths, and the answer sentence is generated by code from the returned rows, so the LLM cannot invent numbers.

## Data storage & cleaning
CSV → pandas validation → SQLite tables `sales` (valid rows, typed, `CHECK` constraints, precomputed `revenue`) and
`rejected_records` (every excluded row with its reason, so nothing disappears silently).

Revenue = `quantity × unit_price − discount_amount` (discount is treated as a per-order total). Dates are DD-MM-YYYY.

| Row | Problem | Handling |
|---|---|---|
| TXN0033 | Status `Returned` | rejected, excluded from revenue |
| TXN0034 | Quantity 0 | rejected |
| TXN0051 | Missing unit price | rejected (price is never guessed) |

48 of 51 rows are used. Total revenue = ₹14,39,200. The UI lists excluded rows under "Data quality".

## API
`POST /ask` `{"question": "..."}` →
`{status, answer, rows, column_types, sql, params, plan, interpreted_by, notes}`.
- `200 status:"ok"` answered · `200 status:"unsupported"` valid request, question can't be answered (message + examples)
- `400` empty or >500-char question · `422` malformed body · `500` internal error (generic message)

`GET /api/meta` (catalog, rejected rows, examples) · `GET /health`.

## Supported questions
Total revenue · top/lowest product, region, category or channel (and "top 3") · revenue breakdown by any of those ·
monthly trend (with month-over-month %) · change between two months · optional filters, e.g. "total revenue in North in March".

## How wrong or unsafe answers are prevented
1. LLM output must pass `validate_plan`: intent whitelist, dimension whitelist, filter values matched against real
   values in the DB (typos fuzzy-matched; unknown values like "Banana" are refused, not guessed), months checked against available data.
2. Only whitelisted column names are placed in SQL; all values are bound parameters.
3. The DB connection is read-only (`mode=ro` + `PRAGMA query_only`), so destructive statements fail even if one slipped through.
4. The user's text is treated as data in the prompt; injection attempts return `unsupported` (see tests 13–14).
5. Answers are templated from query results; the SQL and rows are shown for verification.

## Known limitations
- Revenue is the only metric (no profit, customers, forecasts); only the 5 intents above are supported.
- Rule-based fallback is keyword driven: the word "may" is read as the month May, and complex phrasing may be rejected.
- Single-year data assumed; month names resolve to the latest matching month in the data.
- Discount assumed to be per order, not per unit.
- No auth, rate limiting or caching; each request opens its own SQLite connection.
- The OpenAI path is verified with a mocked LLM in tests; run it once with your own key before submitting.
